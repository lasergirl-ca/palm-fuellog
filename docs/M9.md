# M9: Sync between Palms

Built 2026-11-03 after beaming was verified on the device (M7). A Merge gives the union of
two logs; Sync makes two Palms identical, carrying edits and deletions both ways.

## What was built

- **Sync trailer.** Every record in the five databases ends with 8 bytes: `uid` (random,
  never 0) and `modified` (real seconds since 1904, the clock shift applied; 0 = unknown).
  It follows the fixed part of a vehicle or service type and the terminating NUL of a fill,
  programme or visit, so rc5, the Go reader and old backups still read the record and stop
  before it (`src/records.c`, `RecTrailerPos/Read/Write`). The schema version stays 1.
- **Stamping.** `DbAdd`, `DbReplace` and `DbAppend` write the trailer in place: a uid when
  the record has none, `modified` = now. Off during sync, the clock-shift migration and the
  uid pass (`DbSetStamping`). `DbEnsureUids()` at launch gives every old record a uid.
- **Deletion log.** A sixth database `FuelDel-ZFlg` holds tombstones (db, uid, when; at most
  500, oldest dropped). The five user-delete sites call `DbDelete`; edits still remove and
  re-add without one. Backups include it; a restore of an older set keeps the local one.
- **Bundle kind 3.** The existing `.fuel` framing with every record (trailers included) and
  the tombstones as db 5. `BeamSendLog(vehicle, kind)` sends it; `BeamWriteSyncFile` writes
  it to `Sync/FuelLog-YYYYMMDD.fuel` on the card; Choose a file lists `.fuel` files from
  Sync/ and `BeamImportSyncFile` applies one.
- **Apply** (`src/sync.c`, code section `sync`): per-database tables of uid, modified, index
  and key on the heap; match by uid, else by the Merge's natural key (name; vehicle + date +
  odometer) and adopt the incoming uid; the newer `modified` replaces, otherwise keep local;
  vehicle, programme and type ids remapped to local ids as Merge does; adds appended and the
  fill and visit databases sorted once at the end; tombstones delete a record not edited
  since, and are kept so they travel on to a third Palm; a record deleted here is refused
  when the deletion is at least as new as the record. The rules and the framing are
  host-tested in `tests/test_sync.c`.
- **UI.** Export form: a **Sync** button beside Export. It ignores Format, Vehicle, Range and
  Points and uses Send to: Other Palm (Beam or Bluetooth) or SD card. After a sync lands,
  "Synced: N added, M updated, K deleted. Send this Palm's changes back?" with **Send back**
  and **Done**; Send back goes the same way the bundle came (beam, or a file on the card).
  Log with Merge/Replace is unchanged and still works against rc5.

Known edge: once two Palms have synced they share uids, and a **Log** sent afterwards with
Merge still matches by vehicle, date and odometer only, so a fill whose date or odometer was
changed on one side would be added a second time under the same uid. Between Palms that
sync, use Sync; Log with Merge is for seeding a Palm that has never synced.

A sync that arrives while an edit form is open is held in the inbox and applied when the
fill list next opens, so the record being edited keeps its place.

Compatibility: data from rc5 and earlier reads fine here (old backups restore, old Log
bundles merge, the Go reader is unchanged). The other way has two holes: an rc5 Palm
silently ignores a Sync bundle (the sender still sees Sent), and rc5 cannot read vehicle
records written by this build, since its read buffer is exactly 47 bytes and the record is
now 55. So upgrade both Palms before syncing, and never restore a backup set made by this
build onto an older build. Log bundles beamed to rc5 still work.

Device result (2026-11-03): Zoe ran the sync between the T|X and the LifeDrive: "Works
perfectly". US-37 done.

## What to check with two Palms (both on this build, each launched once)

1. T|X: add a fill, edit another (change the volume), delete a third. Export, Sync, Other
   Palm, Beam. The LifeDrive shows "1 added, 1 updated, 1 deleted"; tap Send back. The T|X
   shows "0 added, 0 updated, 0 deleted".
2. Edit the same fill on both Palms, the LifeDrive a minute later. Sync from either side:
   both end with the LifeDrive's version.
3. Delete a fill on the T|X, then edit that same fill on the LifeDrive. Sync: the edit
   survives on both (an edit after the deletion wins).
4. Sync with Send to: SD card on the T|X; move the card; on the LifeDrive, Choose a file,
   pick the `.fuel`; same summary; Send back writes a file for the way back.
5. A Log bundle from rc5 still arrives with Merge/Replace; a Log bundle from this build still
   arrives on rc5.
6. Backup, Restore, launch twice: the fill count does not change and a Sync afterwards adds 0.
7. About still shows the same record count; the fill list, Stats and Reports look unchanged.
